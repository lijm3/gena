# 周期任务（定时调度）支持方案

> 起草日期：2026/05/18
> 目标：给 gena 增加 cron 风格的**可持久化**周期任务，REPL 重启后任务自动恢复并继续按时触发。

---

## 一、现状与差距

项目目前完全不支持定时执行。和"时间"沾边的机制只有四样，都不是调度：

| 机制 | 真实语义 | 距离"定时任务"有多远 |
|------|---------|---------------------|
| `POLL_INTERVAL` / `IDLE_TIMEOUT` (`config/settings.py:30-31`) | 队友 daemon 空闲时轮询 `.tasks/` 的间隔 | 远——用户无法配置触发时刻 |
| `BackgroundManager` (`managers/background_manager.py`) | 启动后台线程跑**一次** shell 命令 | 一次性，无重复 |
| `TaskManager` (`.tasks/task_<id>.json`) | 持久化任务列表，靠队友空闲时认领 | 没有"到期时间"字段，靠 daemon 抢占 |
| `WALL_CLOCK_TIMEOUT` (`config/settings.py`) | 单次 `agent_loop` 兜底超时 | 防失控，不是调度 |

**缺口**：没有 cron 表达式解析、没有"按时刻触发 prompt/命令"的线程、没有重启后能恢复的调度文件。

---

## 二、设计目标

1. **声明式**：用户用类 cron 表达式描述触发频率（`"0 9 * * *"` / `"*/15 * * * *"`），不要写代码。
2. **持久化**：每个任务一个 JSON 文件（`.schedules/<id>.json`），REPL 退出后再启动，调度器读盘即可恢复。
3. **两种触发动作**：
   - `prompt` —— 把一条 prompt 喂给 **subagent** 执行（**主要场景**）。
   - `bash` —— 直接跑一条 shell 命令（巡检/拉数据/重启服务）。
4. **两种执行语义**（可在每个任务上单独配置）：
   - **提醒型**（`autonomous=false`，默认）：到点把 prompt 塞进 lead 的 inbox，等用户下次回 REPL 时由 `_preprocess` 排空 inbox、和用户消息一起喂给 LLM。**REPL 完全不被打断**、零额外 LLM 调用。
   - **自治型**（`autonomous=true`）：到点调用 **`run_subagent(prompt, subagent_type)`**（`agents/subagent.py`）独立跑——子 agent 自带新的 `LLMClient` / `LoopDetector` / `ProgressTracker` 实例，与主 `MainAgent` **零耦合**；跑完把 outcome 摘要塞进 lead 的 inbox，让用户下次 REPL 看到。真正的无人值守。
5. **并发安全**：
   - 提醒型只写 inbox，无并发问题。
   - 自治型用子 agent，**完全独立、不需要全局锁**；多任务同时触发用一个有界 ThreadPoolExecutor（`SCHEDULER_MAX_CONCURRENT` 默认 2）兜底，避免一窝蜂起子 agent 烧 token。
6. **可控**：用户可在 REPL `/schedule` 命令查看、暂停、删除任务；LLM 也可以通过 `schedule_create / schedule_list / schedule_delete` 工具自己管理。
7. **可观测**：每次触发都在文件里记一笔（`last_run` / `runs` / `last_error`），方便排查。

---

## 三、提醒型 vs 自治型（先理解这个再看后面的技术决策）

方案里反复出现两种"执行语义"，**它们的本质差别决定了什么时候花 LLM token、用户不在场时任务还跑不跑**。理解了这一节，后面的技术决策（§4.3 并发、§4.4 自治型执行流、§5.5 LLM 工具）才好读。

### 一句话区分

> **提醒型** = scheduler 只负责"按时提醒"，**lead 在用户下次对话时才执行**。
> **自治型** = scheduler 按时**立刻派子 agent 执行**，结果回流给 lead。

### 类比

| | 提醒型 | 自治型 |
|--|--|--|
| 类比 | 便利贴 / 闹钟响了 | 雇个临时工 |
| 到点瞬间做什么 | 只写一条 inbox 消息 | 派一个子 agent 去干活 |
| **此刻有没有调 LLM？** | **没有** | **有** |
| 用户回 REPL 时看到的 | "该做 X 了"（任务本身没被执行） | "我做了 X，结果是 …"（已经执行完） |
| 花不花 token | 不花（除了用户回 REPL 后 lead 顺手处理时） | 每次触发都花 |
| 你不开 REPL 时 | 提醒堆在 inbox 里**没人处理** | **照常执行**，结果也堆在 inbox 等你看 |

### 两个具体场景对比

#### 场景 A：每天 9 点提醒我看 PR

**提醒型**：到 9 点，scheduler 往 inbox 塞一条 `[scheduled:morning_pr] 看一下今天有哪些待 review 的 PR`。

- 你 9:30 才回 REPL：lead 这时才打开 inbox，看到提醒，**这时才**真正去调 LLM / `bash gh pr list`，给你列 PR。
- 你 3 天没回 REPL：这条提醒还在 inbox（再加上后续 2 天累计的），等你回来一起处理。
- **本质**：任务被推迟到用户回 REPL 时由 lead 顺手做。

**自治型**：到 9 点，scheduler 立刻派一个子 agent，跑 `gh pr list` → 整理 → 写到 `reports/2026-05-18.md`。跑完往 inbox 塞 `[scheduled-task:morning_pr] 今天有 3 个 PR 待 review：...`。

- 你 9:30 才回 REPL：报告已经生成完了，inbox 里看到的是**结果摘要**，不是"该做的事"。
- 你 3 天没回 REPL：每天 9 点的报告都生成好了，inbox 里堆 3 条结果摘要。
- **本质**：真正的无人值守执行。

#### 场景 B：每 5 分钟检查一个 API 健康

**提醒型**：每 5 分钟塞一条"该检查 API 了"——但你不回 REPL，没人查。等你回来 inbox 里堆了 200 条一模一样的提醒。**这种场景用提醒型完全没意义。**

**自治型**：每 5 分钟子 agent 真去 curl + 报告。你 1 小时后回 REPL，inbox 里是 12 条**实际检查结果**（"健康"×11，"超时一次"×1）。

### 怎么选

| 你的需求 | 选哪个 |
|---------|--------|
| 这事**必须**有用户在场决策（"提醒我去开会"） | 提醒型 |
| 这事**轻量**（一句话提示），并且**只在用户回 REPL 时做才有意义** | 提醒型 |
| 这事**用户不在也得跑**（巡检、定时报告、备份触发） | 自治型 |
| 这事**结果有时效性**（监控指标，过期的结果没用） | 自治型 |
| 想省 LLM token，能省则省 | 提醒型 |
| 用户经常一两天不开 REPL | 自治型 |

### 在 schedule.json 怎么选

字段 `autonomous`：

- `autonomous: false` → 提醒型（默认）
- `autonomous: true` → 自治型，此时 `subagent_type` 字段才有意义（决定子 agent 用 Explore 只读还是 general-purpose 读写）

## 四、关键技术决策

### 4.1 cron 表达式：引入 `croniter`

自实现 cron 解析坑深（天/周混合、闰年、DST），用 `croniter`：
- 单纯依赖、纯 Python、PyPI 上 60M+ 月下载、~50KB。
- API 极简：`croniter("0 9 * * *", base_time).get_next(datetime)`。
- 同时提供 `croniter.is_valid(expr)`，用户写错时能立刻拒收。

`requirements.txt` 追加 `croniter>=2.0.0`。

> 同时**也支持 interval 简写**：`"@every 5m"` / `"@every 1h"` / `"@every 30s"`，内部转成 `croniter` 不能直接吃的格式时退到 `timedelta` 推算。

### 4.2 持久化文件结构

`.schedules/<id>.json`：

```json
{
  "id": "sch_a1b2c3",
  "name": "morning_commit_summary",
  "cron": "0 9 * * *",
  "trigger": {
    "type": "prompt",
    "content": "总结昨天的 git 提交，写到 .reports/<today>.md"
  },
  "autonomous": true,
  "subagent_type": "general-purpose",
  "enabled": true,
  "max_runs": null,
  "runs": 3,
  "last_run": "2026-05-17T09:00:12+08:00",
  "next_run": "2026-05-18T09:00:00+08:00",
  "last_error": null,
  "created_at": "2026-05-15T10:23:00+08:00"
}
```

字段说明：

| 字段 | 含义 |
|------|------|
| `id` | `sch_` + 6 位 hex 短 ID（与 `.tasks/` 数字 ID 区分，避免误删） |
| `name` | 可读名（必填，列表展示用） |
| `cron` | cron 表达式 / `@every Xm` 简写 |
| `trigger.type` | `prompt` \| `bash` |
| `trigger.content` | prompt 文本 / bash 命令 |
| `autonomous` | true → 自治型（起 subagent）；false → 提醒型（只写 inbox） |
| `subagent_type` | 仅当 `autonomous=true` 且 `trigger.type=prompt` 时生效。`"Explore"`（默认，只读）/ `"general-purpose"`（读写）—— 与 `agents/subagent.py` 的 agent_type 一致，最小权限原则默认 Explore |
| `enabled` | 暂停标志，false 时跳过触发不动 next_run |
| `max_runs` | 总触发次数上限（null = 无限），达到后自动 disable |
| `runs` | 累计成功触发次数 |
| `last_run` / `next_run` | ISO8601 + 本地时区偏移；启动时 `next_run<=now` 的直接滚动到下一次 |
| `last_error` | 上次触发抛错时记录 traceback 头 5 行；正常时清空 |

**为什么不放 SQLite**：项目里已经有 `.gena.db` 这个 SQLite，但目前只是 `MessageBus` 自己在用，不想让 scheduler 也依赖它（启动顺序会更脆）。JSON 一文件一任务，复用 `.tasks/` 的同款思路。

### 4.3 并发模型：子 agent 完全独立，无需全局锁

**核心思路**：自治型 schedule 通过 `agents/subagent.py::run_subagent` 起一个子 agent 跑。子 agent 内部新建独立的 `LLMClient` / `LoopDetector` / `ProgressTracker` / 工具 handler 字典，**和主 `MainAgent` 实例零共享**——不存在 loop_detector 状态串扰、不存在 history 污染。

```text
REPL 主线程：               scheduler daemon 线程：
input() →                   每秒 tick →
MainAgent.agent_loop(       发现 next_run<=now →
  user_history)             ThreadPoolExecutor.submit(
       │                        run_subagent(prompt, subagent_type)
       │                    )
       │                    ↓
       │                    子 agent 自带新 LLMClient / 新 LoopDetector
       │                    完全独立的 sub_msgs
       ↓                    ↓
   两条 LLM 调用链各自独立，互不影响
```

- **无需 `agent_lock`**：主 agent 与 scheduler 触发的子 agent **可以同时跑**，互不阻塞 REPL。
- **子 agent 之间也可并发**：用 `ThreadPoolExecutor(max_workers=SCHEDULER_MAX_CONCURRENT)` 兜底，默认 2，避免一次性起 10 个子 agent 同时烧网关额度。超出 max_workers 的任务排队。
- **提醒型（`autonomous=false`）** 不动这套，只是 `bus.send("lead", ...)` 写一行 inbox，下一次 REPL 自然消化。

#### 4.3.1 并发能力对比（按触发类型）

不同 trigger 走不同执行通道，并发上限也不同：

| 触发类型 | 并发能力 | 上限 | 实现位置 |
|---------|---------|------|---------|
| `prompt` 提醒型（`autonomous=false`） | **几乎无限** | 只受文件 IO 限制 | 只调 `bus.send` 写一行 inbox，毫秒级，不占执行槽 |
| `prompt` 自治型（`autonomous=true`） | **受限并行** | `SCHEDULER_MAX_CONCURRENT`（默认 **2**） | `_executor = ThreadPoolExecutor(max_workers=...)` |
| `bash` | **完全并行** | 仅受操作系统进程数限制 | 走 `BackgroundManager`，每次 `threading.Thread(daemon=True).start()` |

**为什么自治型默认 2 而不是 N**：每个子 agent 都自己打 LLM API，开 10 个并发同时跑会撞第三方网关的 rate limit（gpt-5.4 / cngpt 这种网关都有 RPS 限制）。默认 2 保守，用户认为不够可以设 `SCHEDULER_MAX_CONCURRENT=5` 环境变量提上去。

**超出上限时的行为**：
- 自治型：第 3 个任务到点时如果前两个还在跑，进 `_executor` 的**内置队列**等，前面任意一个跑完立刻补位。
- **不会丢失任务**——除非 REPL 中途关机。
- **也不会重复触发**——`_dispatch` 在 submit **之前**就把 `next_run` 滚到下一次，所以即使一个任务在队列里等了 5 分钟，下一次 `_tick` 扫描也不会再次入队。

**调度线程本身不阻塞**：`_tick` 只做"扫描 + submit"，N 个任务同时到点也能在 1 秒内全部派出去；真正耗时的 `run_subagent` 跑在线程池里，跟调度线程隔离。

**和 REPL 完全隔离**：主 agent 在 REPL 主线程跑，scheduler daemon + 执行线程池都是另起的线程，主用户对话和定时任务**真正并发**，互不打断。这是用子 agent 而不是抢 `agent_lock` 的最大收益。

### 4.4 自治型 = 子 Agent 执行 + outcome 回流

每次自治型触发的执行流：

1. `outcome = run_subagent(trigger.content, agent_type=schedule["subagent_type"])`
2. `outcome` 是字符串（子 agent 工作完的最终摘要，由 `run_subagent` 提取 last assistant text 返回）。
3. 把 `outcome` 写到 `.schedules/runs/<id>_<ts>.log`（纯文本，方便 `tail -f` 查看历史）。
4. `bus.send("scheduler", "lead", f"[scheduled:{name}] {outcome[:500]}", msg_type="message")` —— 把摘要塞进 lead inbox。用户下次回 REPL 时 `_preprocess` 自然把它带进对话上下文。

**为什么这样设计**：
- subagent 是用完即弃的——它本身不参与 `microcompact / auto_compact` 这些主 agent 的状态机制。
- subagent 工具集天然是"读为主"（Explore）或"读写"（general-purpose），**没有** `send_message / spawn_teammate / schedule_create`——定时任务不会自己埋点繁殖。
- outcome → inbox 的回流路径已经在项目里了（队友也用这个机制），不引入新概念。

> **限制**：subagent 工具集比主 agent 窄。如果 schedule 任务真的需要 `task_create / send_message` 等副作用工具，目前只能：
>   - 让 schedule 用 `bash` 触发（直接调 git CLI 等）
>   - 或者把 prompt 设计成"分析 X 并把结论写到 reports/<today>.md"——通过文件落地，让 lead 下次读
>   - v2 可考虑给 subagent 增加一个"scheduled mode"工具子集（含 task_create 等，但仍禁止 schedule_create / spawn_teammate）

### 4.5 错过的触发：v1 不补跑

如果 REPL 关机 3 天，期间应该触发 6 次的 `"0 */12 * * *"` 任务怎么办？

**v1 策略**：启动时 `scheduler._load_all()` 发现 `next_run < now`，**直接用 `croniter.get_next(now)` 算下一次**，错过的丢弃。理由：
- "每 12 小时巡检"这类任务，补 6 次没意义；最新一次拿到结果即可。
- "每天 9 点摘要"补跑 3 次只会在 inbox 堆 3 条消息打架。

v2 待办：在 schedule.json 加 `missed_policy: "skip" | "run_once" | "run_all"`，由用户自己挑。

### 4.6 时区

`croniter` 默认按系统 local time 解析 cron 表达式。`last_run` / `next_run` 写入 JSON 时都带本地时区偏移（`datetime.now().astimezone().isoformat()`），便于多地区团队读盘排查。**不引入额外的 `pytz`/`zoneinfo` 配置**——v1 假设单机本地时区，足够覆盖现阶段使用场景。

## 五、实施方案

### 5.1 新模块：`managers/scheduler.py`

核心数据结构与生命周期：

```python
"""
SchedulerManager - 周期任务调度器

线程模型:
  - 一个 daemon 调度线程：每 SCHEDULER_TICK 秒（默认 1s）wake 一次，扫描
    self._schedules 字典，对所有 next_run <= now 且 enabled 的任务 submit
    到执行线程池。
  - 一个 ThreadPoolExecutor（默认 max_workers=2）：实际执行子 agent / bash。
    单个 schedule 跑慢不会阻塞 _tick，下一秒就能继续扫。

为什么不用 sched 标准库:
  sched.scheduler 不支持线程安全的"运行时增删任务"——SchedulerManager 需要
  让 LLM 工具/REPL 命令在运行中动态注册新任务，sched 在这点上不友好。

为什么也不直接用 APScheduler:
  APScheduler 体量大、自带 SQLite/Redis 存储后端会和我们现有 .schedules/*.json 冲突，
  对一个 ~250 行能搞定的需求来说过度工程。
"""
import json
import threading
import time
import uuid
import traceback
from concurrent.futures import ThreadPoolExecutor
from datetime import datetime
from pathlib import Path
from typing import Dict, Any, Optional

from croniter import croniter

from config.settings import (
    WORKDIR, SCHEDULES_DIR, SCHEDULER_TICK, SCHEDULER_MAX_CONCURRENT,
)
from managers.message_bus import MessageBus
from managers.background_manager import BackgroundManager
from agents.subagent import run_subagent
from utils.logging_setup import get_logger

log = get_logger(__name__)


class SchedulerManager:
    def __init__(self, bus: MessageBus, bg_mgr: BackgroundManager):
        """
        Args:
            bus: 用于提醒型触发往 lead inbox 发消息，以及自治型 outcome 回流
            bg_mgr: 用于 bash 触发的后台执行

        注：不需要 agent_run_fn / MainAgent 引用——自治型直接调 run_subagent，
            子 agent 自带新 LLMClient 实例，与主 agent 完全独立。
        """
        self.bus = bus
        self.bg_mgr = bg_mgr
        self._schedules: Dict[str, Dict[str, Any]] = {}
        self._lock = threading.Lock()  # 保护 self._schedules 字典本身
        self._stop_event = threading.Event()
        self._thread: Optional[threading.Thread] = None
        # 执行线程池：自治型 schedule 的实际执行在这里跑，不占调度线程。
        self._executor = ThreadPoolExecutor(
            max_workers=SCHEDULER_MAX_CONCURRENT,
            thread_name_prefix="sched-run",
        )

    # ---- 持久化 ----
    def _path(self, sid: str) -> Path:
        return SCHEDULES_DIR / f"{sid}.json"

    def _load_all(self):
        SCHEDULES_DIR.mkdir(parents=True, exist_ok=True)
        for p in SCHEDULES_DIR.glob("sch_*.json"):
            try:
                data = json.loads(p.read_text(encoding="utf-8"))
            except Exception as e:
                log.error("schedule load failed: %s (%s)", p, e)
                continue
            # 把过期的 next_run 滚到下一次，v1 不补跑
            now = datetime.now().astimezone()
            try:
                next_dt = datetime.fromisoformat(data["next_run"])
                if next_dt < now:
                    data["next_run"] = self._compute_next(data["cron"], now).isoformat()
                    self._write(data)
            except Exception:
                data["next_run"] = self._compute_next(data["cron"], now).isoformat()
                self._write(data)
            self._schedules[data["id"]] = data

    def _write(self, data: Dict[str, Any]):
        self._path(data["id"]).write_text(
            json.dumps(data, ensure_ascii=False, indent=2),
            encoding="utf-8",
        )

    # ---- CRUD ----
    def create(
        self,
        cron: str,
        trigger_type: str,
        content: str,
        name: str,
        autonomous: bool = False,
        subagent_type: str = "Explore",
        max_runs: Optional[int] = None,
    ) -> str:
        if not self._is_valid_cron(cron):
            raise ValueError(f"无效 cron 表达式: {cron}")
        if trigger_type not in ("prompt", "bash"):
            raise ValueError(f"trigger_type 必须是 prompt 或 bash, 实际: {trigger_type}")
        if subagent_type not in ("Explore", "general-purpose"):
            raise ValueError(f"subagent_type 必须是 Explore 或 general-purpose, 实际: {subagent_type}")
        sid = "sch_" + uuid.uuid4().hex[:6]
        now = datetime.now().astimezone()
        data = {
            "id": sid,
            "name": name,
            "cron": cron,
            "trigger": {"type": trigger_type, "content": content},
            "autonomous": autonomous,
            "subagent_type": subagent_type,
            "enabled": True,
            "max_runs": max_runs,
            "runs": 0,
            "last_run": None,
            "next_run": self._compute_next(cron, now).isoformat(),
            "last_error": None,
            "created_at": now.isoformat(),
        }
        with self._lock:
            self._schedules[sid] = data
        self._write(data)
        log.info("[scheduler] created %s name=%s cron=%s next=%s", sid, name, cron, data["next_run"])
        return sid

    def delete(self, sid: str) -> bool:
        with self._lock:
            if sid not in self._schedules:
                return False
            del self._schedules[sid]
        self._path(sid).unlink(missing_ok=True)
        return True

    def list_all(self) -> list:
        with self._lock:
            return list(self._schedules.values())

    def set_enabled(self, sid: str, enabled: bool) -> bool:
        with self._lock:
            if sid not in self._schedules:
                return False
            self._schedules[sid]["enabled"] = enabled
            self._write(self._schedules[sid])
        return True

    # ---- 线程主循环 ----
    def start(self):
        self._load_all()
        self._stop_event.clear()
        self._thread = threading.Thread(target=self._loop, daemon=True, name="scheduler")
        self._thread.start()

    def stop(self, timeout: float = 5.0):
        self._stop_event.set()
        if self._thread:
            self._thread.join(timeout=timeout)
        # 不等正在跑的子 agent，让 daemon 线程随 REPL 退出。
        # 如果将来要"优雅停机"，可以把 wait=True 改成可配置。
        self._executor.shutdown(wait=False)

    def _loop(self):
        while not self._stop_event.is_set():
            try:
                self._tick()
            except Exception as e:
                log.error("[scheduler] tick error: %s", e)
            # 用 Event.wait 替代 time.sleep，stop() 可以立即唤醒。
            self._stop_event.wait(SCHEDULER_TICK)

    def _tick(self):
        now = datetime.now().astimezone()
        # 拷贝一份 ID 列表，避免持锁触发耗时操作
        with self._lock:
            sids = list(self._schedules.keys())
        for sid in sids:
            with self._lock:
                data = self._schedules.get(sid)
            if not data or not data["enabled"]:
                continue
            try:
                next_dt = datetime.fromisoformat(data["next_run"])
            except Exception:
                continue
            if next_dt > now:
                continue
            # 命中触发：调度线程**只滚动 next_run + submit 到执行线程池**，
            # 实际跑（子 agent / bash）在线程池里，不阻塞 _tick 下一秒继续扫。
            self._dispatch(data, now)

    def _dispatch(self, data: Dict[str, Any], now: datetime):
        """命中触发：先滚动 next_run、再 submit 到执行线程池。"""
        sid = data["id"]
        # 先把 next_run 滚动，避免子 agent 跑慢时下一秒重复触发同一任务
        data["next_run"] = self._compute_next(data["cron"], now).isoformat()
        with self._lock:
            self._schedules[sid] = data
        self._write(data)
        log.info("[scheduler] submit %s (%s)", sid, data["name"])
        # 注意：submit 后不 .result()，让 _tick 立即返回
        self._executor.submit(self._fire, data, now)

    # ---- 实际执行：在 _executor 线程池里跑 ----
    def _fire(self, data: Dict[str, Any], fired_at: datetime):
        sid = data["id"]
        log.info("[scheduler] fire %s (%s) trigger=%s autonomous=%s",
                 sid, data["name"], data["trigger"]["type"], data["autonomous"])
        try:
            ttype = data["trigger"]["type"]
            content = data["trigger"]["content"]
            if ttype == "bash":
                # bash 走 BackgroundManager，notifications 队列会被 lead 的 _preprocess 排空
                self.bg_mgr.run(content, timeout=300)
            elif ttype == "prompt":
                if data["autonomous"]:
                    # 自治型：起一个子 agent 跑，outcome 回流到 lead inbox
                    self._run_in_subagent(data, content)
                else:
                    # 提醒型：直接塞 lead inbox
                    self.bus.send(
                        sender="scheduler",
                        recipient="lead",
                        content=f"[scheduled:{data['name']}] {content}",
                        msg_type="message",
                    )
            data["runs"] += 1
            data["last_run"] = fired_at.isoformat()
            data["last_error"] = None
        except Exception:
            data["last_error"] = "".join(traceback.format_exc().splitlines()[:5])
            log.error("[scheduler] fire failed for %s: %s", sid, data["last_error"])
        # max_runs 检查
        if data["max_runs"] and data["runs"] >= data["max_runs"]:
            data["enabled"] = False
            log.info("[scheduler] %s reached max_runs=%d, disabled", sid, data["max_runs"])
        with self._lock:
            self._schedules[sid] = data
        self._write(data)

    def _run_in_subagent(self, data: Dict[str, Any], prompt: str):
        """
        起一个子 agent 跑，把 outcome 写日志 + 塞 inbox。

        关键：子 agent 完全独立——新的 LLMClient / LoopDetector / sub_msgs，
        与主 MainAgent 没有任何共享状态，因此不需要全局锁。
        """
        sid = data["id"]
        agent_type = data.get("subagent_type", "Explore")
        log.info("[scheduler] run_subagent start sid=%s type=%s", sid, agent_type)
        outcome = run_subagent(prompt, agent_type=agent_type)
        # 落日志（仅 outcome 摘要；完整 sub_msgs 不暴露——run_subagent 内部已 log）
        runs_dir = SCHEDULES_DIR / "runs"
        runs_dir.mkdir(parents=True, exist_ok=True)
        ts = int(time.time())
        (runs_dir / f"{sid}_{ts}.log").write_text(outcome, encoding="utf-8")
        # 回流 inbox：lead 下次 _preprocess 时会看到
        self.bus.send(
            sender="scheduler",
            recipient="lead",
            content=f"[scheduled-task:{data['name']}] {outcome[:1000]}",
            msg_type="message",
        )
        log.info("[scheduler] run_subagent done sid=%s outcome_len=%d", sid, len(outcome))

    # ---- cron 计算（含 @every 简写） ----
    @staticmethod
    def _is_valid_cron(expr: str) -> bool:
        if expr.startswith("@every "):
            return SchedulerManager._parse_every(expr) is not None
        return croniter.is_valid(expr)

    @staticmethod
    def _parse_every(expr: str):
        """@every 5m / @every 30s / @every 2h → timedelta"""
        from datetime import timedelta
        body = expr[len("@every "):].strip()
        unit = body[-1]
        try:
            n = int(body[:-1])
        except ValueError:
            return None
        return {"s": timedelta(seconds=n), "m": timedelta(minutes=n),
                "h": timedelta(hours=n), "d": timedelta(days=n)}.get(unit)

    @staticmethod
    def _compute_next(expr: str, base: datetime) -> datetime:
        if expr.startswith("@every "):
            td = SchedulerManager._parse_every(expr)
            return base + td
        # croniter 接受 naive 与 aware datetime，但我们 base 永远 aware
        it = croniter(expr, base)
        return it.get_next(datetime)
```

### 5.3 主入口集成：`main.py`

子 agent 方案下，集成非常简单——没有 lock、没有回调注入、没有 history 序列化。`SchedulerManager` 自己在线程池里调 `run_subagent` 就能跑。

```python
from managers.scheduler import SchedulerManager
from config.settings import SCHEDULER_ENABLED

# 在 BackgroundManager / MessageBus / MainAgent 都创建好之后：

    scheduler.start()
```

`MainAgent.agent_loop` **不需要任何改动** —— scheduler 触发的所有自治型任务都跑在子 agent 里，与主 agent 实例完全独立，没有共享状态需要加锁。这是子 agent 方案相比"主 agent 跑自治"的最大胜利。

### 5.5 LLM 工具：`tools/tool_dispatcher.py`

LLM 也可以自主创建调度任务（例如用户说"以后每天早上 9 点帮我看看 PR 列表"）：

| 工具名 | 入参 | 说明 |
|--------|------|------|
| `schedule_create` | `cron, name, trigger_type, content, autonomous?, subagent_type?, max_runs?` | 创建任务，返回 `sch_xxx` |
| `schedule_list` | — | 全量列出 |
| `schedule_delete` | `id` | 删除 |
| `schedule_set_enabled` | `id, enabled` | 暂停/恢复 |

`schedule_create` 的 input_schema 关键字段：

```json
{
  "type": "object",
  "properties": {
    "cron": {"type": "string", "description": "cron 表达式或 @every Xm 简写"},
    "name": {"type": "string"},
    "trigger_type": {"type": "string", "enum": ["prompt", "bash"]},
    "content": {"type": "string"},
    "autonomous": {"type": "boolean", "default": false},
    "subagent_type": {"type": "string", "enum": ["Explore", "general-purpose"], "default": "Explore"},
    "max_runs": {"type": "integer"}
  },
  "required": ["cron", "name", "trigger_type", "content"]
}
```

`ToolDispatcher` 构造函数新增 `scheduler` 依赖；`get_handler` / `get_tools` 同步两个方法都要改。

**子 Agent 不接入这些 schedule_* 工具**——理由很直接：调度任务由子 agent 跑时，如果子 agent 内部又能 `schedule_create`，就有"调度任务自我繁殖"的风险（一次触发创建 5 条新调度，雪球式炸开）。`subagent.py` 的工具表保持只读/读写两档，scheduler 工具只给主 agent。

### 5.6 与现有机制的边界

| 现有 | 与 scheduler 的关系 |
|------|---------------------|
| `BackgroundManager` | `trigger.type=bash` 的实际执行委托给它；通知机制（`bg_mgr.notifications`）顺带把命令输出送到下次 `_preprocess` |
| `MessageBus.read_inbox` | 提醒型触发 + 自治型 outcome 的落点；`_preprocess` 已有的读取逻辑无需任何改动 |
| `TaskManager` | 互不耦合——scheduled 任务不写 `.tasks/` 文件，避免被队友误抢 |
| `run_subagent` (`agents/subagent.py`) | 自治型触发的执行体；子 agent 自带循环防护与 30 轮硬上限，无需额外加锁 |
| 主 `MainAgent` | **零侵入**：`agent_loop` 不改、不加 `agent_lock`、不注入回调 |

## 七、风险与待确认

1. **`croniter` 在某些边界 cron（如 `"0 0 29 2 *"` 闰年 2/29）的行为**：实施第 3 步时跑一遍 `croniter("0 0 29 2 *", datetime(2026,3,1)).get_next(datetime)` 看返回值是否合理。
2. **子 agent 工具集受限**：subagent 只有 `bash / read_file / read_image / write_file / edit_file` 五件套，没有 `task_create / send_message / load_skill / spawn_teammate` 等高级工具。一些场景（比如"每天早上把 PR 列表创建成 .tasks/"）需要变通：用 `bash` 调 gh CLI + 手写 JSON 到 `.tasks/`，或者用 `write_file` 落地到磁盘后让 lead 下次读 inbox 时人工处理。v2 可考虑给 subagent 加一个 `scheduled-mode` 工具子集（含 task_create，但仍禁止 schedule_create / spawn_teammate）。
3. **`SCHEDULER_MAX_CONCURRENT` 排队**：超出并发上限的任务会在 `_executor` 的内置队列里等。如果一个慢任务卡 5 分钟而期间又有 10 个 cron 触发，队列会堆 10 条。**v1 接受**——首次堆超 N 条时打 warning，让用户看到再决定要不要加 max_workers 或拆任务。
4. **lead inbox 堆积**：提醒型 + 自治型 outcome 都进 inbox；如果用户三天没回 REPL，inbox 会堆 30+ 条。`_preprocess` 一次性塞 `<inbox>` user message 会把 token 拉爆。**缓解**：`MessageBus.read_inbox` 限制每次最多读 N 条（与 `_preprocess` 一起改），多的延后；或者 `<inbox>` 长度过限时只保留最近 N 条。
5. **时区**：v1 跟随系统 local time。如果用户在多机器上跑同一份代码，cron 表达式语义会随时区漂移。**文档明确写"以服务器时区为准"**。
6. **REPL 与 scheduler 同时操作 `.schedules/<id>.json`**：scheduler 已经用 `self._lock` 保护字典，写文件本身是单进程写，原子性由 OS 保证（`Path.write_text`），无需文件锁。
7. **子 agent 跑超时**：`run_subagent` 自带 30 轮硬上限 + LoopDetector + ProgressTracker，但**没有 wall-clock 超时**。如果 LLM 端单次响应卡 5 分钟，会一直阻塞 `_executor` 的一个 worker。**缓解**：v1 接受；v2 给 `run_subagent` 加 wall-clock 超时参数，scheduler 触发时强制设 60s。
8. **`schedule_create` 工具被 LLM 滥用**：模型可能创建一堆奇怪的"每分钟巡检"任务。**缓解**：v1 不做硬限制，但 system prompt 里加一条"调度任务只在用户明确要求时才创建"；v2 加全局 `MAX_SCHEDULES=20`。
