# 图片输入支持方案

> 探测日期：2026/05/18  
> 目标网关：`ANTHROPIC_BASE_URL=https://api.gemai.cc`，`MODEL_NAME=gpt-5.4`

---

## 一、探测结论

用 `tests/test_image_support.py` 与 `tests/test_image_support2.py` 直接对 `/v1/messages` 端点做四组对照实验，结论如下：

| # | 请求形式 | HTTP | 结果 |
|---|---------|------|------|
| 1 | 纯文本（对照） | 200 | ✅ 正常 |
| 2 | Anthropic `image / source.type=base64`（2×2 PNG，极小） | 400 | ❌ "image data ... does not represent a valid image"（疑似最小尺寸校验） |
| 3 | Anthropic `image / source.type=url`（公网 URL） | 500 | ❌ 网关 bug：`failed to decode base64 data ... identifier[base64:data:;base64,%!s(<nil>)]`，URL 没有被网关读出来 |
| 4 | Anthropic `image / source.type=base64`（64×64 PNG，非流式） | 200 | ✅ 模型回复 "分辨率：64×64 像素。主色调：鲜艳的红色"——尺寸和颜色判断准确，确认确实"看到"了图 |
| 5 | Anthropic `image / source.type=base64`（64×64 PNG，stream=true） | 200 | ✅ 与现有 `_consume_stream` 兼容，SSE 文本增量正常累积 |
| 6 | OpenAI `image_url + data URI`（兼容性兜底） | 200 | ❌ 模型回复"请先上传图片"——格式被丢弃，模型未感知到图像 |

**关键结论：**

1. **`gpt-5.4` 模型本身具备视觉能力**，可以解析 base64 内联图。
2. **网关仅支持 Anthropic 原生 `image / source.type=base64`**，URL 模式有 bug，OpenAI `image_url` 格式被忽略。
3. **流式与非流式均可用**，现有 `core/llm_client.py::_consume_stream` 无须改造即可承接含图响应。
4. **小于 ~8×8 的图会被拒**（猜测网关或后端有最小尺寸校验）；后续要给本地图片做"过小则放大"的兜底，或直接报错给用户。

---

## 二、设计目标

把"用户/Agent 把一张图喂给模型"这条链路打通，要满足：

1. **REPL 侧**：用户在 `>>` 提示符可以方便地附加本地图片到下一条消息。
2. **Agent 工具侧**：模型自己也能用一个工具显式"读图"（比如分析磁盘里某张截图）。
3. **历史结构**：图片以 Anthropic Messages 协议的 `image` content block 形式进入 `history`，与现有文本块共存。
4. **预算控制**：图片 base64 极占 token（一张 64×64 PNG = 236 字节 base64，但一张 1280×720 JPEG 可能轻松到 200KB → 约 70K token），**必须**在 `microcompact` / `auto_compact` 时把旧 image block 替换成占位符，否则一两轮就触发预算保护。
5. **子 Agent 同步**：`agents/subagent.py` 拥有独立的工具表，`read_image` 工具要同步过去（否则用户委派的"看图"任务一进子 agent 就废）。
6. **网关边界**：所有图片在客户端一侧统一压成 base64，绝不依赖网关 URL 解析。

## 三、实施方案

### 3.1 新模块：`utils/image_utils.py`

集中放图片相关的纯函数，避免散落到三处。

```python
# utils/image_utils.py
"""
图片处理工具：本地路径 → Anthropic image content block

只支持 base64 内联（探测确认 api.gemai.cc 的 URL 模式有 bug）。
"""
import base64
import mimetypes
from pathlib import Path
from typing import Dict, Any

from utils.path_utils import safe_path

# 允许的 MIME 与文件大小硬上限（避免一张 50MB 截图直接挤爆 token 预算）
ALLOWED_MIMES = {"image/png", "image/jpeg", "image/webp", "image/gif"}
MAX_IMAGE_BYTES = 5 * 1024 * 1024  # 5MB
MIN_IMAGE_BYTES = 200              # 网关对极小图会 400


def guess_media_type(path: Path) -> str:
    mt, _ = mimetypes.guess_type(str(path))
    if mt in ALLOWED_MIMES:
        return mt
    # 默认按 png 处理
    return "image/png"


def file_to_image_block(path: str) -> Dict[str, Any]:
    """
    本地图片 → Anthropic image content block。

    安全：经 safe_path 限制在 WORKDIR 内，不允许 .. 逃逸。
    """
    p = safe_path(path)
    if not p.exists() or not p.is_file():
        raise FileNotFoundError(f"图片不存在: {path}")
    size = p.stat().st_size
    if size < MIN_IMAGE_BYTES:
        raise ValueError(f"图片太小（{size}B），网关可能拒收")
    if size > MAX_IMAGE_BYTES:
        raise ValueError(f"图片过大（{size}B > {MAX_IMAGE_BYTES}B）")
    data = p.read_bytes()
    b64 = base64.b64encode(data).decode("ascii")
    return {
        "type": "image",
        "source": {
            "type": "base64",
            "media_type": guess_media_type(p),
            "data": b64,
        },
    }


def is_image_block(block: Any) -> bool:
    return isinstance(block, dict) and block.get("type") == "image"


def block_short_desc(block: Dict[str, Any]) -> str:
    """给压缩管道用：把 image block 变成可读的占位符。"""
    src = block.get("source", {})
    mt = src.get("media_type", "image/?")
    data = src.get("data") or ""
    return f"[image cleared: {mt} ~{len(data)*3//4}B]"
```

### 3.2 REPL 侧：`main.py`

在用户输入解析里加一个语法：以 `/img <path1> [<path2> ...] | <prompt>` 表示"附图 + 文本"。同时识别行内 `@<path>` 写法以方便快速贴图。

实现要点：
- 把这块解析提到一个小函数 `parse_user_input(query) -> List[Dict]`（返回 Anthropic content block 数组），保持 `main.py` 中已有的特殊命令（`/tasks` / `/team` ...）逻辑不变。
- 解析失败（路径不存在、过大、过小）直接 `print` 错误并 `continue`，不要把异常抛到主循环。

伪代码：

```python
def parse_user_input(query: str):
    """
    支持两种语法：
      1) /img <path> [, <path> ...] | <text>
      2) 普通文本中含 @path/to/img.png → 文本保留，图片插到 text 块前
    返回：Anthropic content blocks 列表（至少一个 text 块）
    """
    blocks = []
    text = query
    if query.startswith("/img "):
        body = query[len("/img "):]
        if "|" in body:
            paths_part, text = body.split("|", 1)
            text = text.strip()
        else:
            paths_part, text = body, "请描述这张图片。"
        for p in [x.strip() for x in paths_part.split(",") if x.strip()]:
            blocks.append(file_to_image_block(p))
    # （可选）行内 @<path> 抽取，留作后续 v2
    blocks.append({"type": "text", "text": text})
    return blocks
```

REPL 主循环里：

```python
try:
    content_blocks = parse_user_input(query)
except Exception as e:
    print(f"[输入解析失败] {e}")
    continue
history.append({"role": "user", "content": content_blocks})
agent.agent_loop(history)
```

### 3.3 Agent 工具侧：新增 `read_image`

让模型在执行任务过程中主动加载图片（比如"看一下 `screenshots/err.png` 然后修 bug"）。

`tools/base_tools.py` 加：

```python
def run_read_image(path: str) -> ToolResult:
    """
    读取本地图片并返回 Anthropic image block（直接嵌入工具结果）。

    注意：tool_result.content 既支持纯文本也支持 content block 列表。
    我们这里返回 [image_block, text_block] 列表，
    让模型在下一轮 LLM 调用里直接"看到"图片。
    """
    try:
        block = file_to_image_block(path)
        return ToolResult(
            content=[block, {"type": "text", "text": f"已加载 {path}"}],
            changed=False,
            done=True,
        )
    except Exception as e:
        return ToolResult(content=f"错误: {e}", changed=False, done=True, error=True)
```

但 `ToolResult.to_llm_format()` 当前只返回字符串，需要扩展为允许返回 list[content block]。改 `utils/loop_control.py::ToolResult`：

```python
def to_llm_format(self):
    # 既存：return f"[{status}] {self.content}"
    if isinstance(self.content, list):
        # content block 列表：把状态前缀以独立 text 块塞到最前面
        prefix = {"type": "text", "text": f"[{self._status_tag()}]"}
        return [prefix, *self.content]
    return f"[{self._status_tag()}] {self.content}"
```

对应 `MainAgent._execute_tools` 里组装 `tool_result` 的地方要保留它原样塞 `content` 字段——Anthropic Messages 协议允许 `tool_result.content` 是 string 或 content block list，**不要 `str(output)` 套一层**。

`tools/tool_dispatcher.py`：
- `get_handler` 加 `"read_image": lambda **kw: run_read_image(kw["path"]),`
- `get_tools` 加：
```json
{"name": "read_image", "description": "Load a local image so the model can see it.",
 "input_schema": {"type": "object", "properties": {"path": {"type": "string"}}, "required": ["path"]}}
```

### 3.4 子 Agent 同步：`agents/subagent.py`

子 agent 的工具表是硬编码的独立副本。要让 Explore / general-purpose 两个 agent_type 都拿到 `read_image`，否则用户委派"分析这张截图"会失败。

最小修改：
- 把 `run_read_image` 加进 handlers
- schema 同步加 `read_image`
- 输出处理保持现状（子 agent 也是 Anthropic 协议，与主 agent 一致）

### 3.5 压缩管道：`utils/compression.py`

**这是最关键的一处**——不处理就会预算炸。

#### 3.5.1 `microcompact`：清理旧 user message 里的 image block

当前 `microcompact` 只清理 `tool_result` 文本。扩展为：

```python
def microcompact(messages):
    # 1) 旧版：清理 tool_result 文本（保持不变）
    # 2) 新增：清理所有"非最近 N 条" user message 中的 image block
    image_carriers = []
    for msg in messages:
        if not isinstance(msg.get("content"), list):
            continue
        for i, part in enumerate(msg["content"]):
            if isinstance(part, dict) and part.get("type") == "image":
                image_carriers.append((msg, i, part))
    if len(image_carriers) <= 2:
        return
    # 保留最近 2 张图，其余替换成 text 占位符
    for msg, i, part in image_carriers[:-2]:
        msg["content"][i] = {
            "type": "text",
            "text": block_short_desc(part),
        }
```

#### 3.5.2 `auto_compact`：摘要前先把所有图替换掉

`auto_compact` 把整个 history 序列化喂给 LLM 做摘要——如果 history 里还有 base64 图，摘要请求自己就会爆 token。处理：

```python
def _strip_images_for_summary(messages):
    cleaned = []
    for msg in messages:
        c = msg.get("content")
        if isinstance(c, list):
            new_c = [
                {"type": "text", "text": block_short_desc(p)} if is_image_block(p) else p
                for p in c
            ]
            cleaned.append({**msg, "content": new_c})
        else:
            cleaned.append(msg)
    return cleaned
```

在 `auto_compact` 内：transcript 落盘**保留原图**（取证用），但摘要前调用 `_strip_images_for_summary(messages)` 再序列化。

#### 3.5.3 `estimate_tokens`：图片 token 校正

当前 `estimate_tokens` 把整个 messages JSON 序列化再 tiktoken 编码——一张 base64 图的 token 估算会被严重高估（base64 ASCII 字符 token 化 ≠ Claude 实际计费）。Anthropic 的图像 token 计费规则约为 `(width * height) / 750`。我们做个简化：

```python
def estimate_tokens(messages):
    # 把 image block 临时替换成固定常量再做文本估算
    IMAGE_TOKEN_EST = 1500  # 一张中等图 ≈ 1500 token，比按 base64 字节估算更接近真实
    cleaned = _strip_images_for_summary(messages)
    text_tokens = _existing_estimator(cleaned)
    image_count = sum(
        1 for m in messages if isinstance(m.get("content"), list)
        for p in m["content"] if is_image_block(p)
    )
    return text_tokens + image_count * IMAGE_TOKEN_EST
```

> 不做这步的话，单图触发 `TOKEN_THRESHOLD=100000` 会把 `auto_compact` 立即烧起来——但实际计费可能只有一两千 token，白白浪费一次 LLM 调用。

### 3.6 队友（teammate）

`managers/teammate_manager.py` 的工具表也是硬编码副本。**当前阶段不接入图片**——理由：
- 队友靠 `.tasks/` 自动认领工作，没有人会主动喂图。
- 队友间通过 `MessageBus` 用 JSON 通信，强行让一个队友把图发给另一个会触碰 SQLite 字段大小问题。
- 等真有用例（比如"截图监控 teammate"）再开。

文档明确写：**队友视觉能力是后续 v2**。

### 3.7 安全与边界

- `safe_path` 已经管路径逃逸，复用即可。
- `MAX_IMAGE_BYTES=5MB` 与 `MIN_IMAGE_BYTES=200B` 作为硬约束，越界直接抛错。
- 不读符号链接外的图（`safe_path` 自带 `is_relative_to(WORKDIR)` 守护）。
- LLM 客户端层不需要改：`base64.b64encode` 出来的 ASCII 字符串经 `requests` JSON 序列化不会触发 UTF-8 问题。

## 五、风险与待确认事项

1. **最小尺寸阈值**：当前知道 2×2 会被拒，但 8×8 / 16×16 临界点未实测。建议在 `image_utils` 里加一个"宽高 < 32 px 时给个友好报错"的预检（用 `PIL.Image.open` 读宽高；如不想引 Pillow 依赖，则保持纯字节大小判断 + 友好错误信息）。
2. **JPEG / WEBP 真实兼容性**：探测只跑了 PNG。提交前最好补 1–2 张真 JPEG/WEBP 的回归。
3. **token 估算偏差**：`IMAGE_TOKEN_EST = 1500` 是经验值，跑几张真实尺寸的图打 `usage.input_tokens` 校准一次（在第 4 步实测时顺便记下）。
4. **图片在 `transcript_<ts>.jsonl` 里完整保留**：单次会话磁盘可能涨快，可选地在落盘前做"超过 N MB 时 base64 → 单独存图 + 路径引用"的优化（非必需，留作 v2）。
5. **网关偶发 400**：探测时偶尔会看到网关返回模糊的 400，建议在 `LLMClient.call_api` 里把 HTTP 400 错误体（含 traceid）保留打印到 `agent.log`，便于后续投诉网关。
